### Recent Changes (2026-08-29)
1. **Critical bug found and fixed: v0.0.16's TypeHandlers were silently encrypting every plain `String` column app-wide (v0.0.16 → v0.0.17)**: the user reported "login이 안됨" (login doesn't work) at `http://192.168.2.57:8080/login`. `/login` itself checked out fine (wrong-password case returned the expected error page), but reproducing end-to-end via a fresh `/register` call threw a 500 - server log showed `PSQLException: value too long for type character varying(50)` on the INSERT. `user_id` (`logintest1`, 10 chars) is the only varchar(50) column among the seven inserted, and the only value in that statement long enough to hit a 50-char cap is a BCrypt hash (60 chars) or an encrypted ciphertext - meaning the plain `#{userId}` parameter (no `typeHandler=` attribute at all) was somehow getting AES-GCM encrypted.
   - **Root cause, confirmed by reading MyBatis 3.5.16's actual source** (extracted `TypeHandlerRegistry.java`/`BaseTypeHandler.java` from the sources jar rather than guessing): `BaseTypeHandler<T> extends TypeReference<T>`, and `TypeHandlerRegistry.register(TypeHandler<?>)` - the exact method Spring Boot's MyBatis auto-configuration calls for every `TypeHandler` bean it finds (`MybatisAutoConfiguration`'s `ObjectProvider<TypeHandler[]>` mechanism) - auto-discovers the mapped Java type via that `TypeReference` when no `@MappedTypes` annotation is present. Removing `@MappedTypes` (done when `EnvelopeCryptoTypeHandler` was first written, specifically to *avoid* this) did nothing, since the `TypeReference` auto-discovery path is independent of that annotation. The upshot: `BoardPasswordTypeHandler`/`UserPiiTypeHandler`, both `BaseTypeHandler<String>` subclasses registered as Spring beans, became MyBatis's *default* handler for the entire `String` type app-wide - not scoped to `board.password`/`users.id_no`/`phone` as intended. Whichever handler won the registration race silently encrypted every other plain `String` `#{...}` parameter with no explicit `typeHandler=`, including `users.user_id` (the one that happened to overflow and throw visibly) and `board.title`/`content`/`author` (which would have silently stored ciphertext with no error, since those columns have no tight length cap).
   - **Fix (vault-crypto `0.0.9 → 0.0.10`)**: `EnvelopeCryptoTypeHandler` now implements the bare `TypeHandler<String>` interface directly instead of extending `BaseTypeHandler<String>` - no `TypeReference` in its hierarchy, so the auto-discovery branch never fires, and registration falls through to "by class only" (exactly the intended, narrow scoping). Method names changed (`setNonNullParameter`→`setParameter`, `getNullableResult`→`getResult`); demoApp's two subclasses needed no changes beyond the version bump. Added a regression test that registers the handler into a real `TypeHandlerRegistry` the same way Spring Boot's auto-configuration does and asserts `getTypeHandler(String.class)` still returns MyBatis's built-in handler, not this one.
   - **Verified via live reproduction, not just reasoning**: confirmed `/register` failed with a fresh test account before the fix, redeployed demoApp `0.0.17` with vault-crypto `0.0.10`, then confirmed end-to-end - `/register` succeeds, `/login` with the new account's real credentials succeeds and reaches the authenticated `/` page, and a REST-created board post's `title`/`content`/`author` land in the DB as plaintext (queried directly via `psql`), not ciphertext. Checked for real user/board data created during the ~20-minute buggy window (`created_date`/`id` range between the two deploys) - found none besides the session's own test rows, which were deleted (`psqltest1`, `logintest2`, the test board post) - so no data corruption to remediate.
   - Lesson for next time: when adding a MyBatis `TypeHandler`, verify its actual registration scope against a real `TypeHandlerRegistry` (as the new regression test now does) rather than trusting that omitting `@MappedTypes` is sufficient - `BaseTypeHandler`'s own class hierarchy can reintroduce automatic type-wide registration independently of that annotation.

6. **Fixed: `/users2` wasn't actually using Redis at all** - the user noticed immediately after deploy. Root cause: classic Spring AOP self-invocation. `UserService.searchCached()` called `this.searchRawCached(...)` directly (an ordinary in-object method call), which bypasses the CGLIB proxy that implements `@Cacheable` entirely - the annotation was present but structurally inert, no exception, no log, just silently never caching. The `@CacheEvict(value = "userSearchRaw", ...)` on `UserService.register()` was unaffected by this bug (evict-annotated methods are always called externally through the proxy, e.g. from `AuthController`, so self-invocation was never a factor there) and didn't need to move.
